## What this release is about

A security release. If you use module access to keep some analysts out of some modules - for example a team that should see Tickets but not Contracts - that restriction hid the screens and stopped changes, but an analyst who knew where to look could still **read** the data behind them. This release closes that, along with two smaller problems found on the way. If every analyst on your install can use every module, the main issue does not affect you, but the second item below does.

**Fixes security issues present in every release from 1.0.0 to 2.10.1.** Upgrade.

## Security

- **Restricted analysts could read data from modules they were not given.** Module access blocked the pages and every change, but most of the requests that *read* data only checked that you were signed in. Someone signed in as an analyst, who knew or guessed the address of one of those requests, could read ticket conversations, contracts and suppliers, asset and software lists, change and problem records, workflows, the system log and more, from modules their teams were never given. They stayed limited to the companies they can access. Every one of those requests now checks module access.

- **Some secret settings were readable by any signed-in analyst.** The signing key behind satisfaction-survey links and the tokens that let scheduled jobs be started over the web were sent in plain text to anyone signed in. With the survey key, someone could submit ratings on a customer's behalf; with a job token, they could start that scheduled job. They are no longer sent. Passwords and AI keys were never exposed - those were already hidden.

- **Four Tickets screens did not check access themselves:** CSAT, Dashboard, the Widget Library and the Triage queue. Their data came through the requests above, but the screens themselves - empty - showed to someone not signed in. All four now check sign-in and Tickets access, like every other screen.

**Do I need to do anything?** Upgrading is enough for most installs. If an analyst you do not trust could have signed in before you upgraded, you can replace the secrets: delete the rows `csat_token_secret`, `sla_cron_token`, `webhook_cron_token`, `workflow_cron_token`, `domain_cron_token` and `integration_cron_token` from the `system_settings` table, then run **System → Database Verification**, which creates new ones. Two things follow. Survey links already emailed to customers stop working. Any scheduled job you start through a web address needs its new address, which `php scripts/cron_token.php --url` prints. Jobs run from the command line are unaffected.

## Fixes

- **A few leftover pages were removed**, including a debugging page that should never have shipped. Nothing used them.

## Upgrading

1. Pull the new code, or rebuild the Docker image.
2. Sign in as an administrator and run **System → Database Verification**. Nothing changes in the database this time, but it is a good habit.
3. Hard-refresh your browser (Ctrl-F5).

**If an analyst now sees "You do not have access to this feature"** somewhere they used to work, their team is missing that module: give it in **System → Teams**. Every changed request was tested as an analyst who has only some modules, and each one was traced to the screens that use it, but please [open an issue](https://github.com/edmozley/freeitsm/issues/new) if you find a screen I missed.

## Rollback

Safe - nothing was removed from the database, so you can go back to 2.10.1 with the code alone. Going back reopens these issues.
